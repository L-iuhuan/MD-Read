## 〇、一句话结论

**原始诉求已达成**（双击 `.md` 能用可用副本打开、可读可改），但**过程中的根因归因有误**：
"exe 所在目录决定成败"这条**观测为真、因果不成立**——它与**时间**（WebView2 运行时 153→154 过渡）和**目录内容**（构建目录有 15 个兄弟条目、副本目录只有 exe）**完全共线**。
同时暴露出一个**真正的产品缺陷（P0）**：已入库的 `[patch.crates-io]` 动态加载器补丁使 exe 在**加载期依赖 `WebView2Loader.dll`**，而该 DLL **既不随包发布、也不入库**——应用目前是**靠 PATH 上 Windows ADK 里一份 2021 年的老 DLL 才跑起来的** ✗。

## 二、被推翻 / 被修正的结论（含 Lead 自己的）【实测】

### 2.1 ✗「exe 所在目录是根因」——观测为真，因果不成立
- 同一二进制（四点 SHA256 全等）确已排除"二进制不同"这一混杂 ✅
- 但**时间混杂致命**：失败在 19:18 / 19:22；**全部成功在 19:55:09 之后**；无 A/B/A。
  `%LOCALAPPDATA%\com.modu.reader\EBWebView` 及其全部子项 **CreationTime = 19:55:09** ⇒ **19:55:09 之前该应用从未成功创建过 WebView2 profile**。
- 窗口内存在机器级事件：WebView2 运行时 **153→154 过渡**（154 目录 18:46:17 建成；`Application` mtime 19:24:29 = 旧版本目录消失；EdgeUpdate 19:25/19:26/19:42 有活动）⇒ **失败窗口被完整夹住**。
- 通路上也不支持：Tauri 在 Windows **强制** UDF = `%LOCALAPPDATA%\<identifier>`（`tauri-2.11.5\src\manager\webview.rs:534-545`）⇒ **exe 目录对 UDF 无作用通路**。
- 另有共线未排除：构建目录 16 项（递归 4895 文件）vs 三个成功目录各 1 项 ⇒ **"位置"与"目录里只有 exe"无法区分**。
- ⇒ **修正表述**：*"19:55 之前在若干位置观察到必失败、之后在若干位置观察到成功"* **成立**；*"位置导致失败"* **未证明** ✗。

### 2.2 ✗「children≥1 ⇒ 启动成功」判据不可靠（两个方向都会错）
- **假阳**：该判据把 `crashpad-handler` / `gpu-process` / `utility` 一并计入 ⇒ 页面未渲染也算"成功"。
- **假阴**：同一 UDF 下 WebView2 **复用**已有 browser 进程 ⇒ 新 app 进程 PPID 下 **0 个子进程**但页面正常；且 `tauri-plugin-single-instance`（mutex = `{identifier}-sim`，**与路径无关**）会让第二实例 **静默 `exit(0)`**（无日志、无窗口、无子进程）⇒ 会被判成"失败"。
- ⇒ **替换判据**（本报告第八节）：数 `--type=renderer` 且 `--user-data-dir` 含 `com.modu.reader` 的进程（不依赖 PPID）+ profile 副作用（`EBWebView\Default\Session Storage\LOCK`、`Local Storage\leveldb\LOG` 的 mtime 是否前进）。

### 2.3 ⭐ `0x800700AA` 的官方语义（此前全程被忽略）
wry 0.55.1 `src\web_context.rs:42,44` 引 MS 文档：
> *WebView creation fails if a running instance using the same user data folder exists, and the Environment objects have different `CoreWebView2EnvironmentOptions`.*

⇒ 该 HRESULT 的语义是**"同一 UDF + 已有实例 + 环境选项不同"**，**与 exe 目录无关**。
⇒ 最可能串起全部现象的机制（**推断，未实证**）：**两种不同版本的 `WebView2Loader.dll`**（ADK `1.0.864.x` vs vendor `1.0.3650.x`）解析出的 browser executable folder / 环境选项不同 ⇒ 命中该语义 ⇒ `ERROR_BUSY`。

### 2.4 ✗ Lead 的其他自纠
- 「提权/受限令牌是变量」：真实语义是"**铸令牌的一方是否提权**"；且 `runas` 在无控制台的计划任务里**必然不可用**（Lead 曾据此交付错误方案）。
- 「护栏：Ready 阶段建 webview 成功」：**空心检查** ✗——`WebviewWindowBuilder::build()` 在 webview 创建失败时**只记日志、Result 仍为 Ok**。
- 「`.md` 关联是我建的」：**反转** ✗——HKLM 的 `.md/.markdown/.mdx → MoDu.*` 由 **MSI 安装器**建立；`Markdown_backup` 值来自 NSIS 的 `FileAssociation.nsh:71` `${FILECLASS}_backup`（更早一次 per-user 安装/卸载的遗留，非本会话所为）。
- 「Defender 区别对待目录」：**推翻** ✗（WinDefend 未运行）。
- 「25 个 `msedgewebview2` 里有孤儿」：**推翻** ✗（分属 Edge / Windows 搜索 / GameViewer / MSPCManager / 正在跑的 modu，**一个都不能杀**）。

## 三、必须修的产品缺陷（P0，建议顺序执行）

### P0-1 ⭐ 动态加载器补丁使应用不可发行
- 事实：`Cargo.toml` 的 `[patch.crates-io] webview2-com-sys = { path = "../vendor/webview2-com-sys" }` **已提交**；`modu/vendor/` **未入库**；两个 exe 都**非延迟加载** `WebView2Loader.dll`；**MSI/NSIS 都不含该 DLL**。
- 后果：① **干净 clone 构建不出来**（CI 今天已红）；② 装到一台 PATH 上没有该 DLL 的机器 ⇒ **应用起不来**；③ 当前之所以能跑，是**借用了 Windows ADK 里的老 loader**（脆弱且不可控）。
- 处置（二选一，**顺序不可颠倒**）：
  - **A（推荐，最小改动）**：撤销补丁 ⇒ 恢复静态链接 loader
    `Cargo.toml` 删除 `[patch.crates-io]` 段 → `cargo update -p webview2-com-sys` → `cargo build` → 验证 `git grep -n vendor` **0 命中** → 最后删 `modu/vendor/`
  - **B（保留补丁）**：把 `WebView2Loader.dll` 随包发布并放在 exe 旁（`build.rs` 已将其拷至 OUT_DIR）+ `git add modu/vendor/`（32 MB 入库）
- ⚠ 无论 A/B，都必须**先做 P0-2 的对照实验**，否则无法判定"静态 loader 是否也能启动"。

### P0-2 ⭐ 补做被推翻实验的**正交判决**（三个实验，每个只改一个变量）
1. **把原凶二进制放回原处**：`D:\modu-loc-test\modu.exe`（`BD667F76…`，与 19:18 那份逐字节相同）复制为 `target\release\modu-ab.exe` 并在该目录运行
   ⇒ **成功** ⇒ "构建目录必失败"被推翻；**失败** ⇒ 位置效应存活，做实验 2
2. **分离"位置"与"目录内容"**（A/B/A 交替，n≥3）：① 同一二进制在 `target\release\`；② 在**新建空目录**；③ 在**空目录里塞 15 个同名兄弟条目**
3. **唯一地翻 loader**（同一二进制 / 同一 UDF / 同一目录）：A=不放假 DLL（走 PATH 的 ADK）；B=放 vendor 的 `1.0.3650.x`；C=放 ADK 的 `1.0.864.x`
   ⇒ 若 A 失败而 B/C 成功 ⇒ 与"补丁方向"一致，并能解释 19:24 之前的失败

### P0-3 判据升级（写进 `AGENTS.md`）
把"应用起没起来"的判据从"PPID 子进程数 / 窗口标题"改为：**`--type=renderer` 且 `--user-data-dir` 含 `com.modu.reader` 的进程数 ≥1** ＋ **profile 副作用 mtime 前进**（两者同时满足才判成功）。

## 六、判据与流程的系统性修正

### 6.1 六步决策树（下次"应用起不来"照此走，每步只改一个变量）
1. **读错误原文**（`[ERROR] tauri_runtime_wry … HRESULT(0x…)`）→ 按 HRESULT 语义查（`0x800700AA` = 同 UDF + 已有实例 + 选项不同；`0x80070005` = 拒绝访问）
2. **确认没有并发实例/僵尸**：`Get-Process modu` + 单实例 mutex `{identifier}-sim`（转发会静默 exit(0)）→ 有⇒先优雅关
3. **确认 UDF 与 loader**：`Get-Process modu | %{ $_.Modules | ? ModuleName -match 'WebView2Loader' }` → 记下**实际加载路径与版本**；`--user-data-dir` 取自命令行
4. **与一个能跑的同类应用对比**（**本会话最有效的一招，却用得最晚**）：同机另一个 Tauri/WebView2 应用能否非提权启动？其安装位置、loader、UDF、版本分别是什么
5. **只改一个变量做 A/B/A**（n≥3，交替）：位置 / 目录内容 / loader 版本 / 运行时版本 / 令牌
6. **判成功要用不可伪造判据**：`--type=renderer` + `--user-data-dir` 匹配 + profile mtime 前进

### 6.2 建议新增到 `AGENTS.md` 的条文（可直接粘贴）
1. **不要修改你正在测量的环境**：任何 `icacls`/注册表/进程强杀动作，先问"这是不是被测对象的一部分"；改了就标注"已污染，读数作废"
2. **失败读数先排"上一次失败的残留"**：单实例转发会让新实例静默退出，症状与"仍然失败"完全一样
3. **判据不得用"能/不能"的单一代理指标**：窗口标题、`build()` 返回值、系统里有没有某进程都会给出假阳性/假阴性
4. **空心检查禁止计入结论**：凡"改 X 后 Y 变了"必须验证 **X 真的生效**（例如 loader 是否真被加载，用 `Modules` 实测）
5. **同机存在"能跑的同类应用"时，先做逐项对比**：这比任何假设推演都快
6. **用户数据一律不"还原基线"**：基线可能本身不干净；只做**增量删除**并保留真实条目
7. **实验产物隔离**：所有一次性脚本/产物进 `.verify/` 并登记；**不得把实验 DLL/依赖留在 `target/` 或 exe 旁**
8. **提交前验证"干净 clone 可构建"**：`[patch]`/`path` 依赖必须连同被指向的目录一起入库
