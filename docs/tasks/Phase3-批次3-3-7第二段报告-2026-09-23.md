## 三、诊断结论 + **批次 5 施工单**（照此做即可）

### 根因（已定位）
`menus` 的**用侧在块外**（工厂返回对象 L485）⇒ 只搬定义侧必然 `TS2304`。

### 施工单
1. `src/app/tab-nav.ts` 的 `setupTabNav` **返回两个方法**：`return { syncNav, syncMenus };`
   其中 `syncMenus = () => menus?.sync();`（**逐字保留原语义**）
2. `tabs.ts` 的返回对象：`syncMenus: () => menus?.sync(),` → **`syncMenus: () => nav?.syncMenus(),`**
3. ⚠️ **关键语义警告（本报告最重要的一条）**：
   > `syncNav()` = `syncScrollButtons()` **+** `menus?.sync()`；而原来的 `syncMenus` **只**调 `menus?.sync()`。
   > ⇒ **绝不能拿 `syncNav` 代替 `syncMenus`** —— 那会**多调一次 `syncScrollButtons`**，是一个**静默差异** ✗
   （重构里最容易溜过去的那类差异的**现成教材**）
4. 解决 `TS6192`（新导入未使用）**不要靠推理**：改完**读实际文件看现场**（导入行 + 调用行）
5. 比对器加**正对照 + 负对照**（拿一对"应当相同/应当不同"的输入各跑一次）
6. 工具纪律：**不要再用生成式变换脚本**做源码手术；用**文件工具逐处小编辑 + 看 diff**

## 四、六条教训（本批新增，建议进全局笔记）

1. **文本替换不懂语法** —— 任何自动化源码变换必须 ① **语法/字符串感知**（不碰字面量、不碰注释）② **带前置断言 + 不成立就中止不写盘**。手工搬移之所以可靠，正因为它慢到每行都被人看过。
2. **沉默 ≠ 通过** —— 检查必须能自证"失败时会报失败"；**"没有输出"一律当"未通过"** ✗（与"检查器报红先检查检查器"是一对）。
3. **比对器要正/负对照自证** —— 假红和假绿一样贵（各花掉一轮）✗（本项目另有一例：敏感门禁的第一次正对照无效，因为 `-Path` 只扫已跟踪文件，后来才补正/负对照）。
4. **先看现场再动手** —— 本轮块 2 第三次尝试**没看实际文件**就带着两处类型错回退 ✗；而最后一次诊断只用了三条 grep 就把谜解开 ✓。
5. **我纠正了 Lead 的建议** —— Lead 提议 `nav?.syncNav()` 防 TDZ；但 TDZ 的 `ReferenceError` 在**读取 `nav` 那一刻**就抛，`?.` 拦不住 ✗。正确做法是**把 `let nav = null` 声明提到所有可能调用之前**（有初值 ⇒ 任何顺序读取都不抛），**赋值仍在原位置**（注册时机逐字不变）。这也是本批真实工作方式的一部分：**建议也要被验证**。
6. **逐字搬移是推断性支撑，不是真机复验** —— 它证明"文本没变"，不证明"运行时没变"。
